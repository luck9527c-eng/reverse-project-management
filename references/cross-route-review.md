# 跨路线条件与影响复查

关键新发现出现时，主动追踪它改变了哪些条件，以及哪些历史路线和下游结论依赖这些条件。**证据可以来自另一条尚未完成的路线；整条 B 完成不是复查 A 的前置条件。**

## 共享条件

只把影响路线选择、结论有效性或重开时机的关键前提和阻塞点登记为 `C-xxx`。复制 [condition.json](../assets/condition.json) 至 `re/conditions/C-001.json`：

- `statement`：可判断的陈述，例如“指定环境中能够获取目标运行时数据”。
- `scope`：具体目标、配置、环境和时间范围；`target_ids` 绑定正式目标。宿主工具能力等环境条件可使用空 target_ids，但必须在 scope 中限定实际主机/环境。
- `state`：unknown / satisfied / unsatisfied，分别表示未知、条件成立、条件不成立；状态描述该陈述，不描述整个路线是否成功。
- `revision`：从 1 递增。条件状态、支持证据或有效性判断发生实质变化时，追加 history 并递增；即使 state 没变，新的相反证据也能触发复查。
- `evidence`：本版本依据的运行 ID，可来自任意路线。history 逐版本保留时间、状态、原因和证据，当前 state/evidence 与最后一项一致。已知状态需要真实运行证据，satisfied 需要完成的有效运行。

条件语义和适用目标发生变化时建立新 ID，保留旧条件及旧结论的边界。避免把“在 A 版本成立”直接改写成“在所有版本成立”。空 target_ids 也不代表所有环境都适用。

路线用 `condition_ids` 引用它依赖的条件。`depends_on` 仍表示路线级的硬依赖：B 的某个发现支持 C，不必因此让 A 依赖整条 B，避免把发现来源误写成循环依赖。

## 自动触发的工作流

每次发现关键新证据、修复工具/观测能力、改变关键配置，或发现旧对照无效时：

1. 保存原始证据和运行上下文，判断哪些现有 C 被支持、反驳或改变适用范围；必要时补建条件关联。不要只在 B 的日志里写“发现突破”。
2. 更新对应条件及其版本历史。证据来自 B 时直接引用 B 的运行，保留目标和来源身份。
3. 执行 `project.py impact <root>`，检查直接引用该条件的路线及其 `depends_on` 下游闭包。已证死、已验证、暂停等状态均参与；没有关联的路线不因这次变化重跑。
4. 对照旧实验的身份、假设、观测链与范围，记录每条受影响路线的复查结果或最小重验计划。路线与条件有关联，只表示需要判断影响，不表示证据可跨目标通用。
5. 执行 `index`，在 INDEX 的“待复查与重验”表保留未处理事项。复查与重验按信息收益、项目优先级和已有预算调度；没有执行预算时记录 deferred、恢复条件和最小下一步。

这是每轮工作和交接中的自动触发规则，不依赖 agent 记住所有旧路线。脚本依据已登记关联和版本计算待办，不做原始输出的语义分析，也不创建后台监控。未登记的关联需要 agent 在发现证据时识别；首次接入、阶段结束和交接时按 [阶段关联审计](acceptance-audits.md#阶段关联审计) 对照全部历史路线与新发现补齐遗漏。待复查为零不能代替这项审计。

## 复查记录与结果

在受影响路线的 `condition_reviews` 中追加记录；直接受影响路线及其下游均记录自己的范围判断。至少包含：

```json
{
  "condition_id": "C-001",
  "revision": 2,
  "at": "2026-10-21T10:00:00Z",
  "outcome": "retest",
  "reason": "B 的新证据使此前观测能力限制需要重新判断；A 尚未重验",
  "evidence": ["RUN-new-b"],
  "next_step": "在声明的触发和窗口下执行一次最小对照实验",
  "stop_when": "沿用当前路线预算；对照失败则记录阻塞并停止"
}
```

| outcome | 含义 | 是否留在 INDEX 待办中 |
|---|---|---|
| unchanged | 已检查新条件的适用范围，旧结论仍成立；记录理由 | 本版本关闭复查 |
| retest | 需要最小重验，尚未完成 | 保留 |
| deferred | 已识别影响，但预算或优先级暂不支持处理；记录恢复条件 | 保留 |
| corrected | 新证据揭示旧判定错误，已记录更正并同步路线状态/历史 | 本版本关闭复查 |
| revalidated | 已完成新的实验，证据支持复查后的判定 | 本版本关闭复查 |

同一版本允许追加多次处理记录，最后一条决定待办进度；过去的记录保留。新条件版本会让此前关闭的复查重新进入待办，即使条件仍是 satisfied。对新版本不适用的旧复查不能消除新待办。

corrected / revalidated 需要实际证据；revalidated 的实验必须已完成。deferred / retest 必须给出 next_step 和 stop_when。若交接时仍有待办，明确其状态，不能把结构校验通过描述为复查完成。

## A 因 B 的发现而需要重验

| 复查发现 | 处置 |
|---|---|
| B 解除了 A 的工具/数据阻塞 | A 进入重验待办；预算允许后更新路线历史并安排最小实验 |
| B 改变了 A 的前提，但旧实验在原范围内有效 | 保留旧 closure 的范围，按新前提重开或建立后继路线 |
| B 证明旧观测链/解释有错 | 引用 B 的证据更正旧判定，检查下游依赖，保存 prior_closure 和更正原因 |
| B 的证据属于其他目标/配置，不能改变 A 的前提 | 记录 unchanged 及不适用理由；新目标可另建条件与路线 |

影响发现不会自动改变路线 status 或覆盖 closure。真正转换状态时仍遵守路线历史和证据门槛；解除一个阻塞不代表其他前提都满足。新的实验创建新运行目录，不覆盖旧负结果。

## 脚本与兼容

- `impact` 只输出待办 JSON，包含条件版本、直接/下游关系、原路线状态、来源证据和已登记下一步；不执行实验或改变路线。
- `index` 自动把相同队列放进导航区，重复刷新不会重复创建复查记录，也不会改写手写区。
- `check` 校验条件身份、版本历史、证据、复查引用和时间，并返回 pending_reviews 数量。该数量为 0 仅表示已登记关联没有待处理项。
- 同一目标范围内，A 可以引用 B 的运行证据；运行仍归属于原路线，原始记录不复制、不改归属。目标 ID/哈希和适用范围继续分别核实。
- 旧项目缺少 condition_ids / condition_reviews 时按空列表处理；升级时比较项目副本差异，补充 condition 模板、impact.py、目录和配置指针，再盘点关键旧记录。共享模板升级不自动覆盖已初始化仓库。
