# 团队协作与编排交接

多 agent 并行或接入编排插件时读取。先读仓库配置中的实际编排契约；没有插件时也可按同样的职责分工协作，单人工作无需启用团队设施。

## 职责与权威记录

| 负责方 | 职责 |
|---|---|
| 本 skill 与仓库配置 | 目标身份、路线与 RUN 结构、证据来源、封存、条件复查、争议和项目验收规则；工具发现、验证、清单/文档维护及缺口提醒 |
| 编排插件（如已启用） | 成员和任务身份、派发交付、并发额度、资源归属、重派与迟到提交处理；把经过核对的结果按本 skill 约定落盘 |
| 整合者（团队中的 Lead） | 选择问题、核对原始来源与判据、确定路线变化、处理跨路线影响和项目验收；通过插件或现有脚本更新权威记录 |
| 执行者 | 在分配的工作区持续保存计划、实际执行、原始产物和局限，提交带定位的结果及路线变更建议 |

沿用 [布局规则](layout.md) 中的权威位置。任务板描述谁在执行；路线文件描述结论及其适用范围；run.json 描述实际执行。岗位、任务与路线/RUN 的映射由编排记录保存，不在另一套文件中维护路线真值。

整合者不执行实验：只选择问题、核对原始来源与判据、确认验收、写共享权威记录。命令类动作（跑脚本、跑工具、编译、调试、版本控制）一律派给执行者完成。同一时刻只有一个整合者写共享权威记录。执行者必须在自己的草稿区记录执行事实，但草稿是核对凭据而不是交付物——交付以结构化回报为准。

## 派发前

整合者依据 [工作会话](work-sessions.md) 筛选问题，检查路线依赖、共享条件版本、争议和遗留实验恢复状态。任务板已完成不能单独证明前提可用；路线的硬依赖需要当前有效的 validated，条件型前提依据具体 C 的版本判断。

每次派发至少说明：

- 项目根、目标 ID/哈希、路线 ID、任务身份和本次尝试身份；运行 ID 由统一分配机制生成，引用后不回收。
- 本轮问题、支持/反对时的判据、预算、停止条件，以及允许读取的前置证据与版本。
- 本次独立工作目录、原始与派生产物位置、需要交回的记录和定位项；指定项目配置、项目 skill 和相关规则入口。
- 工具需求及实际就绪层级、共享资源的归属、可做的动作与限制、卡住和中断时如何交回。

同一调试目标、分析数据库或浏览器会话默认独占，只有确认可共享的读操作才并行。工具名存在最多证明注册可见；运行前按 [环境管理](environment.md) 判断当前执行者的 session_ready 和 target_ready。缺口写成具体阻塞，不以空结果冒充证死。整合者按[工具清单](tool-inventory.md)维护 JSON/Markdown 与不可变快照，插件只读消费；不能用其他执行者的工具集合代替当前执行者的可调用性。

## 执行者记录与提交

执行者在本次独立工作区按 [运行规则](evidence-routes.md#每次运行的记录) 保存计划和实际事实，边干边落盘。团队隔离目录中的记录在归档前是待核对提交，不是第二份已验收路线台账；结论对外引用正式路线与归档后的 RUN。

团队模式下，共享路线、目标、条件、project.json、封存基线和 INDEX 由整合者统一写入；执行者提交建议及其依据。执行者不对共享项目执行 seal/index 或自行改变路线状态。缺少插件时在仓库配置约定独立目录和交接方式，不假定脚本具备并发锁。

提交至少包含：任务/尝试身份、目标与路线绑定、运行清单、产物路径及哈希、观察/推断/假设/未知、原始证据定位、具体阻塞与副作用恢复状态。沿用 RUN 的 completed/failed/timed_out/cancelled/interrupted 语义；尚未开始就阻塞时可以没有 RUN，保存真实的就绪检查和问题，不编造实验。

提交完成即交出该版本写入权；后续更正使用新提交或新尝试，保留旧内容。交付以结构化回报为准：结论、可复跑锚点、未解问题、草稿路径、建议下一步。工作区落盘只作为核对凭据，消息与草稿都不单独替代正式记录；正式记录由整合者写入。执行者报告“交付就绪”，由整合者确认验收；插件采用什么任务板状态应在编排契约中写明。

## 整合者收口

1. **核对交付。** 对照当前任务/尝试、目标身份、前提版本和资源归属，核对原始来源、定位、哈希及记录完整性。过期或已撤销尝试的提交保留为历史，不自动进入当前结论。路径适配只改变存储引用，保存原提交和映射，保持实际命令、cwd、时间、采集事件与字节哈希的真实含义。
2. **归档与封存。** 在串行整合窗口将本次提交归档到正式运行位置；完整写入元数据后才调用 seal。对既有封存复核，校验匹配则复用，冲突按更正规则处理，不能重封存。失败、超时和中断运行同样保留。`seal` 校验全项目，正式记录在命令期间应保持稳定，其他执行者继续写各自隔离区。
3. **更新判定与影响。** 按证据门槛写路线 history/closure，处理条件版本、争议及下游影响，再运行 impact。脚本输出不代做语义判断；未发现、缺工具、预算耗尽不自动映射为 falsified。
4. **校验与回执。** 刷新 INDEX，运行 check --hashes；保留实际检查输出和未闭合事项。结构/哈希错误尚未修复时不宣称整合成功。项目完成另按 [验收与审计](acceptance-audits.md)，不能由任务板全完成推出。

共享权威记录的整合串行化，但独立实验可并行。现有 project.py 提供项目记录检查，不提供成员管理、事务、锁、自动提交验收或后台唤醒；这些能力如需技术保证，由编排实现负责。无法保持正式记录稳定时先停止整合并协调，不放宽封存和校验门槛。

## 重派、恢复与条件变化

重派为新尝试分配新目录和新 RUN ID，撤销旧尝试的提交资格。中断 agent 不证明它启动的进程、驱动或后台任务已结束；按 [中断恢复](evidence-routes.md#中断恢复) 核查并保留部分输出，资源实际可用后再交给下一执行者。

整合后若条件变化影响正在执行的路线，整合者按 impact 和语义审查通知相关执行者，决定继续、暂停或重派；提交时再核对前提版本，不能只在派发时检查一次。新发现可以更新共享条件并触发旧路线复查，无须等整个来源路线结束。

更换 Lead 会话时，事实记录仍可复用，旧成员/任务句柄需重新核查。先确认旧整合者和执行者已停止或隔离，保留旧身份及尝试记录，再按编排契约接管；共享 skill 不自动迁移宿主团队。

## 现有项目接入

在仓库配置登记团队模式、整合者、编排契约位置、独立工作区、资源与写入归属；从 INDEX 手写区链接编排记录入口。新项目可使用更新后的共享模板初始化；已有项目比较项目副本后局部合并本规则和指针，不重新 init 或覆盖历史。编排插件遇到不支持的副本版本应报告缺口，不能静默替换为全局版本。
